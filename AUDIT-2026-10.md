# Security Audit — 0xflare — 2026-10-20

## Summary

Small privacy-hardened Nosflare derivative: three single-file Cloudflare Worker relay profiles (`dm`, `general`, `payment`) plus a Tor-hidden strfry "ghost" variant. Light pass (dm profile read in full; payment/general configs and ghost configs spot-checked). The DM Vault profile enforces kind 4/1059-only writes, forced NIP-42 auth, signature verification, and anti-spam dup hashing — but it has a **privacy-defeating read path**: once any client authenticates (with ANY key), `REQ` returns stored DMs matching the filter with no restriction to the authenticated pubkey. For a relay whose entire purpose is DM privacy, that is a serious design flaw (ciphertext + metadata leakage: sender/recipient pubkeys, timing, sizes).

Findings: 0 Critical / 1 High / 2 Medium / 2 Low

## Findings

| ID | Severity | File/Area | Issue | Recommended fix |
|----|----------|-----------|-------|-----------------|
| FLR-01 | HIGH | `profiles/dm/src/index.ts` `handleReq()` | Any authenticated connection can query and receive **all** stored kind-4/1059 events (up to 200 newest, filterable by author/kind/time). NIP-42 auth is used only as a gate, never to scope reads to events p-tagged to the authenticated pubkey. Gift-wrap metadata (who talks to whom, when) leaks to every user of the vault. | Restrict REQ results to events where the authed pubkey is the author or appears in a `p` tag; reject filters that would widen beyond that. Same for the `broadcast()` path (currently broadcasts every new DM to all connected sessions — `sessions` is never even populated, so broadcast is silently broken AND would leak if fixed naively). |
| FLR-02 | MEDIUM | `profiles/dm/src/index.ts` `newChallenge()` | NIP-42 challenge derived from `Math.random()` + timestamp via SHA-256 — not cryptographically secure; challenges are guessable/predictable, weakening replay resistance. | Use `crypto.getRandomValues` (as nosflare upstream does). |
| FLR-03 | MEDIUM | `profiles/dm/src/index.ts` | Auth event checks challenge + signature but not `created_at` freshness or the `relay` tag; challenge map and `_authed` flag live in-memory/on the WS object while `(this as any).acceptWebSocket(...)` is called instead of `this.state.acceptWebSocket(...)` — hibernation wiring is wrong, so auth state/semantics after DO eviction are unreliable (fails toward requiring re-auth, but the code path is untested-looking). | Check `created_at` window and relay tag; fix hibernation API usage and persist auth state via `serializeAttachment`. |
| FLR-04 | LOW | `README.md` | Attributes nosflare to `fiatjaf/nosflare` — wrong upstream (actual: Spl0itable/nosflare). Cosmetic but confuses fork-freshness tracking. | Fix attribution link. |
| FLR-05 | LOW | `profiles/payment/.dev.vars.example` + wrangler.tomls | Placeholder secrets handled correctly (`LN_API_KEY=your_lnbits_admin_key_here`, `REPLACE_WITH_YOUR_D1_UUID`). Only note: ensure `.dev.vars` is gitignored when profiles are populated (no profile-level .gitignore seen). | Add `.dev.vars` to .gitignore at repo root. |

## Secrets Check

- Reviewed: README, `ghost/{docker-compose.yml,strfry.conf}`, `profiles/payment/{.dev.vars.example,wrangler.toml}`, `profiles/dm/src/*` (config.ts, index.ts, types.ts), profile package.json/wrangler listings.
- GHAS secret scanning unavailable; files read directly.
- **No committed secrets.** Only public npubs/pubkeys and placeholders. Ghost onion key lives in a Docker volume at runtime, not in git — correct.

## Dependency Notes

- dm profile imports `@noble/curves` + `@noble/hashes` (modern, audited libs — good choice over hand-rolled crypto). Profile package.jsons are minimal. `strfry/strfry:latest` and `goldy/tor-hidden-service:latest` in ghost/docker-compose.yml use `:latest` tags — pin digests for the hidden-service stack.

## Fork/Upstream Freshness

Derivative (not a GitHub fork) of nosflare; profiles are rewritten minimal relays, so upstream freshness is not directly comparable. The `general`/`payment` profiles were not read in full this pass.

## Recommended Actions

1. [HIGH] Scope DM-vault reads to the authenticated pubkey (author or p-tag) before operating this profile with real users (FLR-01).
2. [MEDIUM] CSPRNG challenges; created_at/relay-tag checks; fix hibernation wiring (FLR-02/03).
3. [LOW] Fix upstream attribution; gitignore `.dev.vars`; pin Docker image digests (FLR-04/05).
4. Follow-up pass: read `profiles/general` and `profiles/payment` source in full (Cashu/LN admission path deserves a look before mainnet money touches it).
